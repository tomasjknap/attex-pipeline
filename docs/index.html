The unit of analysis

One factual sentence, seven attributes

Criminal verdicts describe the conduct a defendant was found guilty of in a single passage of free text — the factual sentence. Everything a quantitative legal researcher wants is in there, unstructured.

On 24 October 2021 at 22:05, after consuming alcoholic beverages, he drove a Škoda Felicia passenger car […] and was stopped and checked by a police patrol […], and subsequently underwent breath tests […], with an Alcotest 7510 device […] recording 1.27 mg/l of alcohol in his breath on 24 October 2021 at 22:08:21, and a repeated breath test using the same device […] recording 1.09 mg/l of alcohol in his breath on 24 October 2021 at 22:42:11, and he did not request a blood sample to be taken.

Date Driving time Vehicle Test method Device Alcohol level Test time

English translation of a shortened Slovak factual sentence, omissions marked […]. A single sentence may hold several events and measurements: structuring it requires separating the time of driving from the test times and pairing each measured value with the test that produced it.

Abstract

Attributes that cannot be specified in advance

Criminal verdicts contain descriptions of criminal behavior that could support quantitative legal research, but structuring them requires attributes and extraction rules that cannot always be fully specified in advance. We present a pipeline combining attribute exploration, extraction of supporting text spans, and value normalization, guided by an annotation manual that legal experts can refine.

Experiments on two traffic-related offense categories reveal difficulties shared by human annotators and LLMs when instructions are underspecified. For driving under the influence, revising the manual was associated with an increase in overall class accuracy from 51.8% to 69.6% and higher human agreement. Consistent LLM outputs did not guarantee agreement with reference annotations. These findings support iterative dataset creation in which expert review informs both verification of extracted values and refinement of extraction rules.

Pipeline

Three stages, one manual

The annotation manual is the shared specification: the same document instructs the human annotators and configures the extraction prompts. Researchers revise it, and the accepted manual regenerates annotations across the whole corpus.

Annotation manual = extraction schema
attribute ID · description · cardinality · value format · category labels
STAGE 1

Attribute exploration

Statements are processed in fixed-size batches against the current schema. Residual information not covered by existing attributes goes to an LLM, which proposes candidates for subsequent batches. The researcher decides which are retained.

src/a_attribute_explorer.py
STAGE 2

Span extraction

Evidence is extracted as copied text, aligned with the original statement, then wrapped in XML-like tags with unique identifiers. Later stages reference the identifiers instead of relocating the evidence.

src/d_dataset_builder.py
STAGE 3

Value normalization

Value types, output formats, normalization rules and — where appropriate — categories are derived from the values actually observed in the corpus, preserving information while minimizing interpretation.

src/c_semantic_normalizer.py
Human-in-the-loop revision cycle
LLM drafts a new manual · revision requested in natural language · researcher inspects values and supporting spans

Spans are written back as <span id="s1">Škoda Octavia</span>, so every extracted value stays traceable to the text that supports it. A fourth script, src/e_format_validator.py, checks a finished dataset against declared variable constraints.

Induction batch size controls granularity

On the same 200 statements, pooling residuals in batches of 100 produced 39 attributes — a third of them populated in under 5% of sentences. Batches of 200 produced 30 attributes, with 13% under that threshold.

Rarity is not a pruning rule

activeDrivingBan appears in 3.5% of statements and attemptedBribeOrCorruption in 0.5% — both can still matter to the research question. The induced schema is a set of candidates for expert review, not a finished specification.

Repeatability is not correctness

Repeated runs of the same model agreed with each other far more than with other models or with curated annotations. Where humans, models and gold labels all disagree — as for reasonForCheck — the category itself needs a more explicit decision rule.

Get started

Induce a schema in one command

Python 3.13 and uv. The provider key is read from the environment — OPENAI_API_KEY, GENAI_API_KEY, GROQ_API_KEY or UFAL_API_KEY.

git clone https://github.com/tomasjknap/attex-pipeline
cd attex-pipeline
uv sync

uv run src/a_attribute_explorer.py \
  --input data/dui_dev_sample.csv \
  --output dui_schema_induced.json \
  --initial-attributes data/initial_attributes.json \
  --provider openai --model gpt-5.6-terra \
  --schema-update-batch-size 100 \
  --population-threshold 0.85

--schema-update-batch-size is the induction batch size N from the table above: smaller batches see less evidence per induction call and propose more case-specific attributes.

Data & scope

What the repository contains

  • Attribute schemas and the annotation manual for both offence categories — driving under the influence (DUI) and driving despite an imposed ban (DDB).
  • The 200 sampled factual sentences per category used in the experiments, plus a DUI development sample.
  • Extracted spans and values for DDB, the input to value normalization.
  • Prompt templates for every stage and the YAML variable constraints used by the format validator.

Factual sentences are passages from Slovak criminal court judgments issued between 2018 and 2022. Experiments are restricted to single-offence judgments, which account for 68% of the 126,795 judgments in the source collection.

Not included: the full judgment corpus, the annotation interface used to collect the human reference annotations, and scripts recomputing the agreement figures reported in the paper.
